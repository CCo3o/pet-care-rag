# 共享档期与预订体验

目的：让 A 确认预订后，B 在另一段对话也能查询到最新占用。模型负责理解自然语言，Python 工具读取共享 SQLite 数据库，不靠模型记住旧余位，也不把订单放进 RAG 文档。

这是本地模拟门店，不是真实订单或支付系统。容量来自 `data/booking_capacity.json`，猫标准间默认每天 2 个位置。每笔预订占 1 个位置，包含结束日：1—4 日占用四天，5 日释放。单次最多 366 天是演示输入限制，不是门店政策。

## 亲手体验：两个终端扮演两位顾客

在 VS Code 新建两个终端，均进入本项目目录。旧助手先输入 `exit` 退出；两个终端分别运行：

```powershell
.\.venv\Scripts\python.exe -m app.main
```

不需要重建知识库。以下预期以这些日期尚无订单为前提；已有演示订单会保留，可换一段未使用的日期。

1. B 问：`一只猫标准间，2026年10月1日至4日都有位置吗？` → 每天已订 0 个，还剩 2 个。
2. A 说：`我要预订（或“我要预定”）一只猫的标准间，2026年10月1日至4日。` → 展示待确认草案，尚未占位。
3. B 再问原问题 → 仍然剩 2 个。
4. A 下一条输入：`确认预订`或`确认预定` → 保存本地演示预订，显示编号。
5. B 再问原问题 → 每天已订 1 个，还剩 1 个。注意，有人订了不等于已经满了。
6. B 问：`猫标准间2026年10月4日至5日还有位置吗？` → 4 日已订 1 个，5 日已订 0 个。
7. B 输入 `/clear`，或退出重启后再问 → 已保存占用仍在。清聊天不是退订。

A 若在草案之后继续聊天或修改条件，旧草案会失效，需要重新提出预订并核对。连续重复“确认预订”不会再占一个位置。询价与预订目前分开处理，预订草案不代表已经核价或付款。

## 代码为什么这样设计

- `app/chat.py`：理解房型和日期；信息不足先追问；生成草案，只有用户明确确认才进入保存流程。
- `app/bookings.py`：每次查询重新统计已保存订单；确认时在同一个数据库写事务内重新检查并占位，避免两人同时抢到最后一个位置。
- `data/bookings.sqlite3`：不同终端共享的持久化订单，首次查询时自动创建。顾客只看到汇总数量，不看到他人订单信息。
- `data/booking_capacity.json`：模拟房型容量，不是实际门店库存。

当前的本地演示支持取消已保存订单：同一会话可说“取消我刚才的预订”，新会话需提供完整订单编号。取消采用保留记录、标记取消的方式，档期会立即释放；仍不提供支付、身份认证或多宠多间预订，不能当作可直接上线的真实预约系统。

## 验证与面试理解

离线测试（不调用模型）：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

真实自然语言联调（少量 API 费用，只写临时数据库，不污染演示订单）：

```powershell
.\.venv\Scripts\python.exe -m evaluation.booking_smoke --live
```

体验后试着自己解释：为什么清聊天不影响订单？为什么新预订不需要重建向量索引？为什么查询有位后，确认时还要重新检查？这三个问题对应会话状态与业务数据分离、动态数据工具查询、并发超卖保护。有限测试通过不意味着所有自然语言表达都能正确识别。
